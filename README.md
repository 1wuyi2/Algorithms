# 学院级智能排课系统

本项目定位为一个基于图染色与约束优化的学院级智能排课网站。当前主线只做老师端的学院自动排课，先完成排课算法的基础数据层和冲突关系层，再逐步实现贪心图染色排课和回溯搜索优化。

当前不做学生端个性化推荐、AI 辅助排课、真实教务系统对接等功能，这些内容作为后续扩展方向。

## 当前阶段目标

第一阶段不直接写完整排课系统，而是先完成排课算法的三个基础部分：

1. 数据建模：定义课程、教师、班级、教室、时间槽等数据结构。
2. 冲突检测：实现判断两门课程是否冲突的函数。
3. 冲突图构建：根据课程之间的冲突关系构建冲突图。

这三个部分完成后，后续的贪心图染色排课和回溯优化都可以基于它们继续开发。

## 总体模块划分

项目建议按模块化方式开发，每个模块尽量保持独立，方便小组成员分工、测试和修改。

```text
Algorithms/
├── README.md
├── src/
│   ├── models/          # 数据模型
│   ├── config/          # 学校规则配置，例如南开校区和时间槽规则
│   ├── data/            # 模拟数据
│   ├── constraints/     # 冲突检测
│   ├── graph/           # 冲突图构建
│   ├── algorithms/      # 排课算法
│   ├── evaluation/      # 课表评价与优化
│   └── utils/           # 工具函数
└── tests/               # 测试用例
```

如果暂时不确定最终技术栈，也可以先用简单脚本或控制台程序实现核心逻辑，后面再接入网站前后端。

## 子任务拆分

### 任务 1：数据模型模块

目标：定义排课系统中最基础的数据结构。

主要内容：

- 定义 `Course` 课程结构
- 定义 `Teacher` 教师结构
- 定义 `ClassGroup` 班级结构
- 定义 `Room` 教室结构
- 定义 `TimeSlot` 时间槽结构

建议字段：

- 课程：课程编号、课程名称、授课教师、上课班级、课时数、可选时间、教室类型要求
- 教师：教师编号、姓名、不可用时间、可授课程
- 班级：班级编号、专业、年级、人数
- 教室：教室编号、容量、教室类型、可用时间
- 时间槽：星期、节次、开始时间、结束时间

输入：无，主要负责定义数据结构。

输出：一组可以被其他模块使用的数据类型。

完成标准：

- 每个核心实体都有清晰字段
- 字段命名统一
- 后续模拟数据、冲突检测、算法模块可以直接引用

### 任务 2：模拟数据模块

目标：在没有真实教务数据的情况下，提供开发和测试用数据。

主要内容：

- 编写若干教师数据
- 编写若干班级数据
- 编写若干教室数据
- 编写若干时间槽数据
- 编写若干课程数据

输入：数据模型模块定义的数据结构。

输出：一组可直接用于测试的模拟数据。

完成标准：

- 数据量不用太大，但要能覆盖常见冲突情况
- 至少包含教师冲突、班级冲突、教室容量不满足等情况
- 后续模块可以直接导入这批数据进行测试

### 任务 3：冲突检测模块

目标：判断两门课程是否不能同时安排。

主要内容：

- 判断两门课是否使用同一个教师
- 判断两门课是否面向同一个班级
- 判断两门课是否固定在同一时间
- 判断课程人数是否超过教室容量
- 判断教师、教室或班级在某个时间是否不可用

第一阶段可以先实现最核心的三类冲突：

- 教师冲突
- 班级冲突
- 固定时间冲突

输入：两门课程，以及必要的教师、班级、教室、时间槽信息。

输出：是否冲突，以及冲突原因。

完成标准：

- 提供一个类似 `hasConflict(courseA, courseB)` 的函数
- 能返回简单的冲突结果
- 最好能说明冲突类型，方便调试和页面展示

### 任务 4：冲突图构建模块

目标：根据课程之间的冲突关系构建冲突图。

图的含义：

- 每门课程是一个节点
- 如果两门课程不能安排在同一时间槽，就在两个节点之间连一条边

主要内容：

- 遍历课程列表
- 两两调用冲突检测函数
- 如果存在冲突，则在冲突图中添加边
- 输出邻接表或邻接矩阵

输入：课程列表、冲突检测函数。

输出：课程冲突图。

完成标准：

- 能正确输出每门课程和哪些课程冲突
- 能用简单示例数据验证图结构是否正确
- 输出格式能被后续图染色算法直接使用

### 任务 5：贪心图染色排课模块

目标：基于冲突图快速生成一个可行课表。

主要内容：

- 将时间槽看作颜色
- 将课程看作图中的节点
- 按一定顺序遍历课程
- 为每门课选择一个不与相邻课程冲突的时间槽

输入：冲突图、课程列表、可用时间槽。

输出：课程到时间槽的分配结果。

完成标准：

- 能在小规模模拟数据上生成无硬冲突课表
- 排课失败时能指出哪些课程无法分配
- 算法逻辑清楚，方便后续优化

### 任务 6：回溯搜索 / 约束满足模块

目标：作为贪心算法的对比算法，也可以用于优化结果。

主要内容：

- 逐门课程尝试分配时间槽
- 遇到冲突时回退
- 尝试寻找更完整或质量更高的排课方案

输入：课程列表、时间槽列表、冲突检测函数或冲突图。

输出：一个可行课表，或排课失败原因。

完成标准：

- 能在小规模数据上找到可行解
- 能和贪心算法结果进行对比
- 代码结构便于加入更多约束

### 任务 7：课表评价模块

目标：评价生成课表的质量，为后续优化提供依据。

可评价指标：

- 是否存在硬冲突
- 教室容量是否满足
- 教师课程是否过于集中
- 班级课程分布是否均衡
- 教室利用率是否合理

输入：排课结果、课程信息、教师信息、班级信息、教室信息。

输出：课表评分或问题列表。

完成标准：

- 能检查课表是否有明显冲突
- 能输出简单评价结果
- 后续可以作为局部优化算法的依据

### 任务 8：老师端页面模块

目标：为学院老师提供基础排课操作页面。

可规划页面：

- 基础数据管理页面
- 自动排课页面
- 课表展示页面
- 冲突提示页面

第一阶段页面不是重点，可以先用控制台输出结果。等核心算法模块稳定后，再接入网页展示。

输入：后端或算法模块输出的数据。

输出：可视化课表和冲突提示。

完成标准：

- 能展示课程、教师、班级、教室等基础数据
- 能展示生成后的课表
- 能展示排课失败或冲突原因

### 阶段二任务 1：数据导入模块

目标：将南开大学选课手册 PDF、CSV 或 Excel 中的课程信息导入系统。

主要内容：

输出：可被系统读取的标准课程数据。

### 阶段二任务 2：后端 API 模块

目标：把已有 Python 模型、冲突检测、冲突图、贪心排课、回溯搜索和课表评价模块封装成网站接口。

建议接口：

- `GET /health`：检查服务状态
- `POST /schedule/greedy`：运行贪心图染色排课
- `POST /schedule/backtracking`：运行回溯搜索排课
- `POST /schedule/evaluate`：评价课表质量

输出：前端可直接展示的 JSON 数据。

当前基础版已经完成，代码位于 `src/api/`。因为真实数据导入后置，暂时不实现 `POST /courses/import` 和 `GET /courses` 这类持久化接口。

本地启动方式：

```bash
python -m src.api.server
```

默认服务地址：

```text
http://127.0.0.1:8000
```

## 南开大学规则配置

当前已经根据已知信息加入南开大学排课规则配置：

- 排课周期：周一到周日
- 每天节数：14 节
- 是否有晚课：有
- 排课时间范围：早 8 点到晚 10 点
- 晚饭时间：17:40 到 18:30，暂不排课
- 课间休息：上午前两节课后休息 20 分钟，下午前两节课后休息 20 分钟，其余课间休息 10 分钟
- 校区：津南校区、八里台校区

注意：当前没有加入真实课程、教师、班级、教室数据。后续可以单独做数据导入模块，支持教务处导入 Excel、CSV 或数据库数据。

## 选课手册 PDF 数据处理计划

后续如果使用南开大学选课手册 PDF，可以单独建设数据导入模块，目标是把课程信息转换为系统可识别的 `Course`、`Teacher`、`ClassGroup` 等结构。

建议处理流程：

1. 先识别 PDF 类型：可复制文字、表格型 PDF、扫描图片 PDF。
2. 抽取课程号、课程名、学分、周学时、任课教师、开课学院、课程类别、上课对象等字段。
3. 将抽取结果转换为统一的中间数据格式，例如 CSV、JSON 或数据库表。
4. 做字段校验和人工复核，避免 PDF 识别错误直接进入排课算法。
5. 通过数据导入模块写入系统，再进入冲突检测、冲突图构建和排课算法。

注意：如果 PDF 是扫描图片，需要额外 OCR；如果 PDF 内部是复杂跨页表格，也需要先做清洗和人工校验。真实数据导入前，不应直接覆盖当前模型或算法代码。

## 开发原则

- 先完成基础数据结构，再写算法。
- 先实现可运行的小模块，再组合成完整系统。
- 每个模块都要有明确输入和输出。
- 没有真实数据时，先用模拟数据验证逻辑。
- 第一目标是无硬冲突，第二目标才是课表更优。
